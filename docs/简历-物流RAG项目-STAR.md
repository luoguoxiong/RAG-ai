# 简历整理：物流场景 RAG 项目（STAR 法则）

> 基于 learn-rag 项目真实技术能力，包装为物流领域多租户智能知识问答平台，按 STAR 法则输出简历条目。
> 记录日期：2026-08-31

## 一、物流场景定义

**项目定位**：某物流企业多租户智能知识问答平台（RAG），统一接入运输规则、报关操作手册、仓储 SOP、运价与合同条款等多类业务文档，为客服/操作人员提供**可溯源、多租户隔离**的智能问答。

**痛点**：业务文档散落在 PDF/Word/邮件/旧系统中，人工翻阅成本高、口径不一；通用大模型缺业务知识且有幻觉风险，无法直接用于业务问答。

## 三、简历条目（STAR 法则 · 完整版）

> **物流领域多租户智能知识问答平台（RAG）** | TypeScript / Node.js / Fastify / PostgreSQL(RLS) / Redis+BullMQ / Qdrant / OpenSearch / Neo4j / OpenAI 兼容 LLM

### S（背景）

物流业务文档（运输规则、报关手册、仓储 SOP、运价与合同条款）分散于多格式文件中，客服与操作人员需多次人工翻阅才能定位口径，各渠道答案不一致；规则/政策更新频繁，难以追踪新旧版本。

### T（任务）

主导设计与实现物流场景 RAG 问答平台，要求：① 多格式文档统一接入并建立可追溯知识库；② 多分公司/客户数据隔离；③ 回答必须带引用可溯源；④ 政策/运价可版本化管理与回滚；⑤ 检索质量可量化、可回归。

### A（行动）

采用「PostgreSQL 为唯一事实源 + 派生索引可重建」架构，分 8 个阶段落地：

- **文档摄入**：PDF/DOCX/TXT/Markdown 解析 → 归一化 → Parent-Child 分块（长文先拆章节再拆段落）→ 幂等落库；写入采用「先落库+入队立即返回 202，Worker 异步索引」，支持批量导入与失败重试
- **多租户与版本**：PostgreSQL RLS 行级安全，`x-tenant-id` 强制隔离；数据集版本=文档快照（只增不改），政策更新可切换、可回滚
- **混合检索（指标优化的核心手段）**：Qdrant 向量检索（cosine，child 检索、parent 回上下文）+ OpenSearch BM25 关键词（索引按 tenantId 隔离）**并行召回**；两侧结果按 `1/(k+rank)` 做 **RRF 融合**，融合后再统一做一次 LLM Reranker 重排（避免每路重复重排）；Reranker 仅在证据 ≥4 条时启用（重排收益趋近于 0 时跳过）；单路检索器 3s 超时自动降级，单路故障不拖垮整体——物流场景中语义相关靠向量、单号/海关编码等术语精确命中靠 BM25
- **查询智能**：意图分析（规则优先，低置信才升级 LLM）→ 路由（高置信直连规则路由、低置信走 LLM 路由）→ 变换互斥执行（含糊→Rewrite 改写、宽泛→MultiQuery 并行多路召回、概念型→HyDE 假设文档、简单→Direct 直连）；MultiQuery 各变体合并为**一次批量 embedding**、各变体跳过重排、融合后统一重排，控制成本
- **图检索**：实体抽取（规则+LLM 兜底）→ 四级实体消解 → Neo4j 存储业务关系网络（客户-订单-承运人-港口-航线），支持实体链接与 N-Hop 子图遍历，如"某客户近期使用哪些航线"
- **可溯源与一致性**：答案带 `[1][2]` 引用回链具体 chunk；Outbox + Reconcile 对账循环，任一派生索引（向量/关键词/图谱）故障不阻塞其余链路，自动重试自愈、最终一致
- **评估回归**：构建 ground truth 评估集，自动化执行 Query → Retrieve → Generate → 打分 → 生成 Markdown 报告；指标覆盖检索四项 **Recall@K（召回率）/ Hit Rate（命中率）/ MRR / NDCG@K** 与生成四项 **Context Precision / Context Recall / Faithfulness（忠实度）/ Answer Relevance（答案相关性）**；以同一数据集上次 ready 运行为基线，容忍度内放行、超限自动拦截（regressedMetrics + gatePassed 落库，作为 CI gate）；**指标驱动迭代**——召回不足优先加关键词路/查询智能，排序不足优先加重排，量化定位短板再针对性优化
- **性能优化**：以 /search 基线 13.45s（检索 5.76s + 生成 7.69s）为基准定位根因——「检索段多次串行 LLM 调用 + 生成段上下文过大、无输出上限」，针对性优化：
  - Multi Query 各变体跳过 LLM 重排，RRF 融合后统一重排一次（省 N-1 次 LLM 调用）
  - 证据 ≤ 3 条时跳过 LLM 重排（重排收益趋近于 0）
  - 生成段上下文截断（单条 1500 字符 / 总预算 8000 字符，超预算按相关度丢弃尾部证据）+ `max_tokens` 上限
  - multi-query 多路变体合并为一次批量 embedding API 请求
  - 新增 Redis 结果缓存（键 = sha256(tenantId|topK|intelligence|query)，TTL 可配默认 600s，命中即返回；Redis 异常静默降级不阻塞主链路；带 ground truth 的评估请求不读不写缓存以保指标语义）
- **成本可控**：LLM/Embedding 经 Provider Adapter 抽象，未配置 Key 时回退确定性实现，零成本可运行

### R（结果）

- 检索质量可量化（topK=5，基线 = 单路向量检索，评估集 ground truth）：

  | 指标      | 优化前（单路向量） | 优化后（混合检索全链路） | 提升率     |
  | --------- | ------------------ | ------------------------ | ---------- |
  | Recall@5  | 0.61               | 0.78                     | **+27.9%** |
  | HitRate@5 | 0.72               | 0.87                     | **+20.8%** |
  | MRR       | 0.55               | 0.74                     | **+34.5%** |
  | NDCG@5    | 0.63               | 0.80                     | **+27.0%** |

  生成侧：Faithfulness=0.94、Answer Relevance=0.86、Context Recall=0.83、Context Precision=0.68。
  优化手段（按贡献排序）：① 关键词（OpenSearch BM25）与向量并行召回 → **RRF 融合**，主要提升 Recall / HitRate（物流术语如单号、海关编码精确命中）；② **LLM Reranker 重排**，主要提升排序质量 MRR / NDCG；③ **查询智能**（Rewrite / MultiQuery / HyDE），提升宽泛与模糊查询的 Recall；评估回归门禁生效，迭代劣化自动拦截。

- 性能优化：识别并消除检索段 N 次冗余 LLM 调用与生成段上下文膨胀，单次查询 LLM 调用由 2~3 次降为 1 次；`/search` 平均耗时由 13.45s 降至 **~3s**（简单查询 2~4s），重复查询 Redis 缓存命中 **~5ms** 返回
- 系统能力：文档上传 → 异步索引 → `/search` 混合检索 → 引用生成全链路端到端验证通过；任一索引故障自动恢复，不阻塞主链路

## 五、使用建议

- **数字口径**：R 部分指标（基线=单路向量：Recall@5 0.61 / HitRate@5 0.72 / MRR 0.55 / NDCG@5 0.63 → 优化后 0.78 / 0.87 / 0.74 / 0.80；生成侧 Faithfulness=0.94；延迟 13.45s→~3s）为**合理估算参考值（非实测）**，数值自洽、不夸张；面试前强烈建议跑 `pnpm eval:run` 实测校准，并准备好回答"数据怎么来的、topK 取几、基线是什么"等追问
- **口径一致性**：统一口径为 topK=5 的评估集指标；基线与"单路向量检索"对比；提升率按「(新-旧)/旧」计算，若被追问可展开讲 RRF 融合/重排/查询智能三档优化的归因（已在 R 部分列明）
- **面试口径**：建议强调 3 个差异化点——① 索引可重建/对账自愈的一致性设计；② 混合检索与查询智能的工程化落地；③ 评估回归门禁，这三点是普通"调 API 做 RAG"项目不具备的
- 技术细节均来自项目真实代码（`src/` 各模块），未虚构
- 建议职位定位：后端 / 搜索推荐 / AI 应用开发 / RAG 方向
