# 切片（Chunking）设计文档

> 对应代码：[src/ingestion/splitters.ts](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/splitters.ts)、[src/ingestion/parser.ts](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/parser.ts)、[src/application/ingestion.ts](file:///Users/kye/Documents/ai/learn-rag/src/application/ingestion.ts)

## 1. 设计目标

切片环节要同时满足三个目标：

1. **检索精准**：小块做向量/关键词召回，命中率高。
2. **上下文完整**：命中后需要把整段上下文喂给 LLM，避免只见树木不见森林。
3. **语义完整**：不做字符级硬切（会把一句话、一段代码拆碎，破坏语义）。

因此采用 **Parent/Child 两级切片**（Parent-Child Retrieval 模式），并按文档类型分发不同的切分策略。

## 2. 核心概念：Parent / Child 两级

| 层级       | 目标大小   | 职责                                                      | 是否进检索索引  |
| ---------- | ---------- | --------------------------------------------------------- | --------------- |
| **child**  | ~400 字符  | 检索单元，向量/关键词索引的最小粒度                       | ✅ 是           |
| **parent** | ~2000 字符 | 上下文单元，命中 child 后用其所属 parent 回填上下文喂 LLM | ❌ 否（仅存库） |

- child 只存检索所需的最小语义片段；
- parent 由相邻 child 贪心聚合而成，保证上下文完整；
- 检索命中 child → 回表其 `parentId` → 用 parent 内容作为 LLM 上下文（见 [retriever.ts](file:///Users/kye/Documents/ai/learn-rag/src/retrieval/retriever.ts) 的 `assembleEvidence`）。

## 3. 架构：与 Parser 对称的分发设计

切分层与解析层对称：解析按文件类型分发（parser.ts），切分也按文档类型分发。

```
文档 → Parser（按类型） → ParsedDocument{ text, language, ... }
                          ↓
              splitterFor(language) → Splitter
                          ↓
              ParentChildChunk[]（parent + children）
```

- [Splitter 接口](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/splitters.ts#L8-L13)：`supports(language?)` 判断是否适用，`split(text)` 返回 parent/child 两级结构。
- 分发依据是解析器写入的 `metadata.language`（如 markdown / pdf / docx）。
- 所有切分器统一返回 `ParentChildChunk[]`，下游 `processVersion` 的哈希、落库逻辑完全不变（零侵入）。
- 注册表 [splitters](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/splitters.ts#L196-L201)：MarkdownSplitter 在前（专用优先），SentenceSplitter 在后兜底（`supports()` 恒为 true）。

## 4. 通用切分器：SentenceSplitter（text / pdf / docx）

[代码](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/splitters.ts#L63-L76)

```
splitSentences（分句）
   → toChildren（句子 → child，超长句独立成块）
      → toGroups（child → parent/child 组）
```

### 4.1 分句：splitSentences

按中英文句号/问号/感叹号/分号切分，lookbehind 正则保留分隔符在句尾：

```ts
text.split(/(?<=[。！？；.!?;])\s*/);
```

句子保持完整，**不做字符级硬切**，避免语义碎片化。

### 4.2 句子聚合为 child：toChildren

- 逐句累积，加入下句会超 `CHILD_MAX`（400 字符）时闭合当前 child；
- 单句超长时该句独立成块（不硬拆句子）。

### 4.3 child 聚合成 parent：toGroups

- 逐 child 累积，`parent.length + child.length + 2 > PARENT_MAX`（2000）时闭合当前组；
- `+2` 是 `"\n\n"` 分隔符的长度，parent 组内 child 以空行连接。

## 5. Markdown 专用切分器：MarkdownSplitter（结构感知）

[代码](file:///Users/kye/Documents/ai/learn-rag/src/ingestion/splitters.ts#L151-L193)

Markdown 有标题层级，直接按句子切会丢失"这段属于哪一节"的信息。因此 MarkdownSplitter 增加结构感知：

### 5.1 按标题分节：splitByHeadings

- 按 ATX 标题（`#` ~ `######`）把文档切成分节；
- 标题作为节的**语义锚点**。

### 5.2 节内拆块：splitBlocks

节内容按行拆成三种块：

| 块类型                | 处理方式                                           |
| --------------------- | -------------------------------------------------- | -------------------- |
| 围栏代码块（` ``` `） | **整体保留**为一个块，不拆散（拆开会破坏代码语义） |
| 表格块（连续 `        | ` 行）                                             | **整体保留**为一个块 |
| 普通段落（直到空行）  | 保留内部换行，后续再按句子细分                     |

### 5.3 块 → child

- 代码块 / 表格：**整体作为一个 child**（可能超长，但拆开结构就坏了）；
- 普通段落：走 `splitSentences` + `toChildren` 按句子聚合。

### 5.4 带标题前缀的 parent 聚合

- parent 以 `# 标题` 作为前缀，检索命中后可定位"来自哪一节"；
- parent 超长时按 child 分片闭合，**每个分片仍带标题前缀**（保证上下文可定位）。

## 6. 关键参数

| 常量         | 值       | 含义                                               |
| ------------ | -------- | -------------------------------------------------- |
| `CHILD_MAX`  | 400      | child 目标字符数，控制向量召回粒度                 |
| `PARENT_MAX` | 2000     | parent 目标字符数，超过则另起一组                  |
| 分隔符       | `"\n\n"` | parent 组内 child 的连接符（长度 +2 计入上限判断） |

## 7. 切片完整工作流

切片不是孤立的一步，而是横跨 **API 受理 → 队列 → Worker 消费 → 切片落库 → Outbox → 派生索引** 的完整链路。受理方只写元数据与 Job，重活由 Worker 异步完成，从而让 API 立即返回、与索引解耦。

涉及表（详见 §8）：`documents` / `document_versions` / `jobs`（受理）→ `chunks` / `index_status` / `outbox`（消费 + 派生）。

### 7.1 阶段总览

```
[API 进程: ingestDocument]        [Worker 进程: processVersion]      [Reconciliation]
  解析 → 归一化 → 哈希              切片 → 清理过期 → 幂等落库           消费 outbox
  落库 documents/                  投递 chunk.upserted 到 outbox       写向量/关键词/图索引
       document_versions/          标记 version/document = ready      更新 index_status
       jobs
  入队 index_document Job ───────→ BullMQ 拉取 → markJob(processing)
  返回 202 + jobId                 分发到 processVersion / delete ───→ 扫描 pending 事件
```

### 7.2 受理阶段：ingestDocument（API）

[代码](file:///Users/peroluo/Document/github/RAG-ai/src/application/ingestion.ts#L37-L114)

API 收到上传请求后 **只受理不切片**，在一个事务内完成（任一失败整体回滚，避免孤儿状态）：

1. **解析**：`parserFor(fileName, mimeType).parse(...)` 按文件类型选解析器，提取纯文本、标题、`metadata.language`（切片阶段据此分发 splitter）。
2. **归一化**：`normalize(parsed.text)` 去空白/统一换行，保证哈希稳定。
3. **内容哈希**：`hashContent(text)` = sha256(归一化文本)，作为版本去重/幂等依据。
4. **事务落库**：
   - `documents`：`status=pending`、`sourceType=file`、`sourceUri=原始文件名`；
   - `document_versions`：`version=1`、`contentHash`、`rawContent=归一化文本`、`metadata={...language, title}`、`status=pending`；
   - `jobs`：`type=index_document`、`status=pending`、`payload={documentId, versionId}`。
5. 返回 `{documentId, versionId, jobId}`，由调用方把 Job 入队 `rag-index`，响应 `202 Accepted`。

### 7.3 消费阶段：Worker 拉取与分发

[代码](file:///Users/peroluo/Document/github/RAG-ai/src/worker.ts#L26-L75)

Worker 是独立进程，与 API 解耦：

1. BullMQ `Worker` 从 `rag-index` 队列拉取 Job（`concurrency=4`，单进程并发 4 个）。
2. `reconciliation` 是系统对账任务，直接 `runReconcile()` 返回，不落 Job 状态。
3. 业务 Job 先 `markJob(tenantId, jobId, "processing")`，再按 `job.name` 分发：
   - `index_document` / `reindex_document` → `processVersion(versionId, tenantId)`；
   - `delete_document` → `deleteDocument(documentId, tenantId)`。
4. 成功 `markJob(..., "ready")`；失败 `markJob(..., "failed", msg)` 后重新抛错，由 BullMQ 按重试策略再次派发，DB 的 Job 状态兜底可重试语义。
5. 另有定时器周期性触发 `runReconcile()`，兜底修复任何一次消费失败。

### 7.4 切片落库阶段：processVersion（核心）

[代码](file:///Users/peroluo/Document/github/RAG-ai/src/application/ingestion.ts#L162-L284)

切片真正的核心，在 `withTenantTx` 单事务内 7 步完成：

1. **加载版本**：`loadVersion(tx, versionId, tenantId)` 带租户校验；不存在直接跳过（版本可能已被删）。
2. **取归一化文本与标题**：`normalize(version.rawContent)`；标题取自 `metadata.title`，将作为 chunk 的 `metadata`。
3. **选切分器**：`splitterFor(metadata.language)` —— markdown 走 `MarkdownSplitter`（标题感知），其余走 `SentenceSplitter`（句子级）。所有 splitter 统一返回 `ParentChildChunk[]`，下游哈希/落库逻辑不变。
4. **分块 + 预计算稳定哈希**（[hashChunk](file:///Users/peroluo/Document/github/RAG-ai/src/lib/hash.ts#L16-L20)）：

   ```
   plans = splitter.split(text).map(group => ({
     parentContent, parentHash,        // kind="parent"
     children: [{content, hash}]       // kind="child"
   }))
   ```

   `hashChunk = sha256(documentVersionId + "\n" + kind + "\n" + normalizedContent)`，**kind 区分 parent/child**，避免两级内容相同时哈希碰撞。

5. **清理过期 chunk**（先清后插，保证 `chunkIndex` 唯一连续）：
   - 汇总"期望哈希集合" `desiredHashes`（所有 parentHash + childHash）；
   - 查出现存 `chunks where documentVersionId = versionId`，凡 `contentHash` 不在期望集合中的即过期；
   - **先删 `index_status` 再删 `chunks`**（避免外键/唯一索引冲突），并为每个被删的 chunk 投递 `chunk.removed`。
6. **幂等落库**（[insertChunkIfAbsent](file:///Users/peroluo/Document/github/RAG-ai/src/application/ingestion.ts#L129-L151) + `onConflictDoNothing` on `(documentVersionId, contentHash)`）：
   - `chunkIndex` 全局递增（`idx++`），版本内顺序唯一；
   - **parent 先插拿到 parentId，child 后插并回填 parentId**，构建两级引用；
   - 重复处理同一版本只会得到同一批 chunk（稳定哈希 + 唯一索引），可安全重跑。
7. **投递 Outbox + 标记 ready**：
   - 为该版本所有 chunk 投递 `chunk.upserted` 事件（Reconciliation 据此写派生索引，**仅 child 落检索索引**）；
   - `document_versions.status = ready`；`documents.status = ready` 且 `currentVersionId = versionId`。

### 7.5 派生索引阶段：Reconciliation + Outbox

切片落库只写 `chunks` 与 `outbox`，**不直接写向量/关键词/图索引**——这是切片与索引解耦的关键：

1. `processVersion` 在同事务内把 `chunk.upserted` 写入 `outbox`（与业务变更同事务，不会丢事件）。
2. Reconciliation 周期性扫描 `outbox where status=pending and availableAt <= now()`，按 `eventType` 分发：
   - `chunk.upserted` → 写派生索引（向量/关键词/图），更新 `index_status`；
   - `chunk.removed` → 清理对应派生索引。
3. 失败用指数退避重试（`attempts+1`，`availableAt = now() + 2^attempts 秒`），成功 `markOutboxDone`。
4. 切片落库成功即对用户"可见"（chunks 已就绪），派生索引最终一致地补齐。

### 7.6 删除阶段：deleteDocument

[代码](file:///Users/peroluo/Document/github/RAG-ai/src/application/ingestion.ts#L290-L315)

单事务内：查 `chunkIds` → 删 `index_status` → 逐个 `emitChunkRemoved` → 删 `chunks` → 删 `document_versions` → `documents.status=deleted`、`currentVersionId=null`（软删，保留行可追溯）。

## 8. 数据表的完整过程

切片链路涉及 6 张表，按"写入顺序"梳理每张表的角色、字段，以及在工作流各阶段的状态流转。schema 定义见 [src/db/schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema)。各阶段每张表的状态变化汇总见 §8.7。

### 8.1 documents（文档主表）

[schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema/document.ts#L12-L32)

| 字段                       | 含义                                                  |
| -------------------------- | ----------------------------------------------------- |
| `id` / `tenantId`          | 主键 / 租户隔离                                       |
| `versionId`                | 独占归属的数据集版本（外键 `restrict`，版本不可删改） |
| `sourceType` / `sourceUri` | 来源类型与 URI（Phase 1 为 `file` + 原始文件名）      |
| `title`                    | 解析提取的标题                                        |
| `status`                   | `pending` → `ready`（切片完成）/ `deleted`（软删）    |
| `currentVersionId`         | 当前生效版本，切片完成时回填                          |

状态流转：受理 `pending` → processVersion 收尾 `ready` + 回填 `currentVersionId` → 删除 `deleted` + 置空 `currentVersionId`。

### 8.2 document_versions（文档版本表）

[schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema/document.ts#L34-L50)

| 字段          | 含义                                                     |
| ------------- | -------------------------------------------------------- |
| `version`     | 版本号，首次为 1                                         |
| `contentHash` | sha256(归一化文本)，版本去重依据                         |
| `rawContent`  | 归一化后的纯文本（切片输入；Phase 1 暂存 PG，后续迁 S3） |
| `metadata`    | `{language, title, ...}`，`language` 决定 splitter 分发  |
| `status`      | `pending` → `ready`                                      |

状态流转：受理 `pending`（已存 rawContent 待切片）→ processVersion 成功 `ready`。本表是切片的**输入源**：rawContent 经归一化后送入 splitter。

### 8.3 jobs（任务表，受理侧）

受理阶段写入，Worker 消费时驱动状态机：`pending`（入队前落库，可追溯）→ `processing`（Worker 拉取）→ `ready`（成功）/ `failed`（失败，可重试）。`payload={documentId, versionId}` 指向待处理实体。**jobs 只在受理与消费阶段流转，切片本身不直接读写它。**

### 8.4 chunks（切片核心表）

[schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema/chunk.ts#L13-L43)

| 字段                                            | 含义                                                      |
| ----------------------------------------------- | --------------------------------------------------------- |
| `id`                                            | 随机 uuid 主键（落库后由 outbox 事件引用）                |
| `tenantId` / `documentId` / `documentVersionId` | 三级归属，均级联删除                                      |
| `type`                                          | `parent` / `child`                                        |
| `parentId`                                      | child 指向其 parent 的 id；parent 为 null                 |
| `content`                                       | 切片文本（parent=上下文，child=检索单元）                 |
| `contentHash`                                   | `hashChunk(versionId, kind, content)`，稳定 ID + 幂等依据 |
| `chunkIndex`                                    | 版本内全局递增，保证顺序唯一（依赖先清后插）              |
| `metadata`                                      | `{title}` 等                                              |
| 唯一索引                                        | `(documentVersionId, contentHash)` —— 幂等落库的物理保证  |

写入过程（processVersion 步骤 5–6）：

1. **清理**：算出过期 chunk，先删 `index_status` 再删 `chunks`，并投 `chunk.removed`；
2. **落库**：`chunkIndex` 递增；**parent 先插**拿到 id，**child 后插**回填 `parentId`；`onConflictDoNothing` 保证重跑幂等；
3. 全部落库后为每个 chunk 投 `chunk.upserted`。

检索侧（[retriever.ts](file:///Users/peroluo/Document/github/RAG-ai/src/retrieval/retriever.ts)）：按命中的 childId 回表 child → 收集 `parentId` 批量回表 parent → 用 parent 内容作 LLM 上下文，`chunkId` 仍指向 child。

### 8.5 index_status（派生索引状态表）

[schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema/chunk.ts#L45-L60)

| 字段                                  | 含义                             |
| ------------------------------------- | -------------------------------- |
| `chunkId`                             | 主键 + 外键到 chunks（级联删除） |
| `vector` / `keyword` / `graph`        | 三类派生索引状态，默认 `pending` |
| `embeddingModel` / `embeddingVersion` | 向量索引的模型溯源               |
| `updatedAt`                           | 最近更新时间                     |

**切片阶段不写本表**——它由 Reconciliation 消费 `chunk.upserted` 后异步写入。删除 chunk 时级联清空。`pending` → `done`/`failed` 的流转发生在派生索引阶段。

### 8.6 outbox（事件表，切片与索引解耦的枢纽）

[schema](file:///Users/peroluo/Document/github/RAG-ai/src/db/schema/outbox.ts#L12-L36)

| 字段                            | 含义                                           |
| ------------------------------- | ---------------------------------------------- |
| `aggregateType` / `aggregateId` | `chunk` + chunkId                              |
| `eventType`                     | `chunk.upserted` / `chunk.removed`             |
| `status`                        | `pending` → `done` / `failed`                  |
| `attempts`                      | 重试次数                                       |
| `availableAt`                   | 指数退避后的可投递时间                         |
| 索引                            | `(status, availableAt)` 供 Reconciliation 扫描 |

写入：与 chunks 落库**同事务**（[emitChunkUpserted](file:///Users/peroluo/Document/github/RAG-ai/src/application/outbox.ts#L31-L37) / [emitChunkRemoved](file:///Users/peroluo/Document/github/RAG-ai/src/application/outbox.ts#L40-L46)），不丢事件。消费：Reconciliation 扫描 `pending` 事件 → 写 `index_status` → `markOutboxDone`；失败 `markOutboxFailed` 指数退避重试。

## 9. 检索侧如何使用两级结构

[assembleEvidence](file:///Users/peroluo/Document/github/RAG-ai/src/retrieval/retriever.ts#L71-L114)：

1. 按命中的 childId 回表 child 行；
2. 收集 child 的 `parentId`，批量回表 parent 行；
3. 组装 Evidence 时，`content` 取 **parent 内容**（parent 缺失时退回 child 内容），作为 LLM 上下文；`chunkId` 仍指向 child（保持引用精确）。

这样做到：**用 child 召回（精准），用 parent 作答（完整）**。

## 11. 设计要点总结

1. **两级结构**：child 召回精准，parent 上下文完整，二者兼顾。
2. **分类型分发**：与 Parser 对称，Markdown 结构感知，其余句子级切分。
3. **句子完整性**：不做字符级硬切；代码块/表格整体保留为 child。
4. **标题语义锚点**：Markdown 的 parent 带标题前缀，命中可定位章节。
5. **幂等落库**：稳定 contentHash + 唯一索引，重复处理安全。
6. **解析前提**：PDF 解析先做段落还原（合并硬换行），否则切分会把同一段落切成碎片。
