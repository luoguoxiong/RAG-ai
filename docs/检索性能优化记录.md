# 检索性能优化记录（/search 延迟 13.45s → 目标 6~8s）

> 发生时间：2026-08-31
> 相关代码：[src/application/query.ts](file:///Users/kye/Documents/ai/learn-rag/src/application/query.ts)、[src/retrieval/retriever.ts](file:///Users/kye/Documents/ai/learn-rag/src/retrieval/retriever.ts)、[src/query/index.ts](file:///Users/kye/Documents/ai/learn-rag/src/query/index.ts)、[src/cache/search.ts](file:///Users/kye/Documents/ai/learn-rag/src/cache/search.ts)、[src/config.ts](file:///Users/kye/Documents/ai/learn-rag/src/config.ts)

## 1. 现象与基准

压测 /search 平均指标：

| 指标 | 均值 |
| --- | --- |
| 平均耗时 | 13.45s |
| 平均检索 | 5.76s |
| 平均生成 | 7.69s |
| 平均引用 | 4.0 |

耗时自洽：13.45s ≈ 5.76s + 7.69s。瓶颈集中在「检索段多次串行 LLM 调用」与「生成段上下文过大、无输出上限」。

## 2. 耗时分析（根因）

配置了 API key 且 Query Intelligence 开启时，/search 链路的外部调用：

1. **变换（Rewrite / Multi Query / HyDE）**：触发时 +1 次 LLM；
2. **Embedding**：+1 次 HTTP API；
3. **LLM Reranker**：+1 次 LLM，且**整个证据全文塞进 prompt**；
4. **生成**：+1 次 LLM，上下文 = 全部证据全文，无 max_tokens 上限。

典型查询 = 2~3 次 LLM + 1 次 embedding，每次火山方舟调用 1~3s，累计即 5.76s。

最贵场景是 **Multi Query（宽泛查询）**：N 个变体并行各自再付 1 次 embedding + 1 次 LLM 重排，且 embedding 未批量合并。

## 3. 优化方案与实施

### 3.1 Multi Query 每路去掉 LLM 重排，融合后统一重排一次

- 问题：`retrieveEvidenceMulti` 把 `useReranker=true` 传给每个变体，N 路各付一次 LLM 重排，而多路召回本来就要 RRF 融合，每路重排多余。
- 改法：各变体传 `useReranker: false`（仅按融合分召回），RRF 融合出 topK 后统一做**一次** LLM 重排。
- 位置：[src/query/index.ts](file:///Users/kye/Documents/ai/learn-rag/src/query/index.ts)

### 3.2 证据 ≤ 3 条时跳过 LLM 重排

- 问题：简单查询只有 2~3 条证据时仍无条件 LLM 重排，收益趋近于 0。
- 改法：`retrieveEvidence` 中 `evidence.length < RERANK_MIN_EVIDENCE(4)` 时直接按融合分返回；常量导出供 multi-query 统一重排复用。
- 位置：[src/retrieval/retriever.ts](file:///Users/kye/Documents/ai/learn-rag/src/retrieval/retriever.ts)

### 3.3 生成段：上下文截断 + max_tokens 上限

- 问题：`buildMessages` 把每条证据全文塞进 prompt；`generateAnswer` 不传 `maxTokens`，模型可能写超长。
- 改法：
  - 单条证据正文上限 1500 字符，上下文总预算 8000 字符；证据按相关度排序，超预算的尾部证据丢弃（LLM 自然不会引用）；
  - `generateAnswer` 传 `maxTokens: 1024`。
- 位置：[src/application/query.ts](file:///Users/kye/Documents/ai/learn-rag/src/application/query.ts)

### 3.4 Embedding 批量（multi-query 一次 API 请求）

- 改法：`Retriever.retrieve` / `VectorRetriever.retrieve` 增加第 5 参 `vector?: number[]`；`retrieveEvidenceMulti` 先 `getEmbedding().embed(queries)` 批量嵌入一次，各变体复用对应向量，避免 N 路重复调用 API。
- 位置：[src/retrieval/retriever.ts](file:///Users/kye/Documents/ai/learn-rag/src/retrieval/retriever.ts)、[src/query/index.ts](file:///Users/kye/Documents/ai/learn-rag/src/query/index.ts)

### 3.5 Redis 结果缓存 (tenantId, query, topK) → citations

- 键：`sha256(tenantId | topK | intelligence | query)`；
- TTL：`SEARCH_CACHE_TTL` 环境变量，默认 600 秒，0 关闭（[src/config.ts](file:///Users/kye/Documents/ai/learn-rag/src/config.ts)）；
- 实现：新增 [src/cache/search.ts](file:///Users/kye/Documents/ai/learn-rag/src/cache/search.ts)，复用 [src/queue/index.ts](file:///Users/kye/Documents/ai/learn-rag/src/queue/index.ts) 的共享 ioredis 实例；
- 接入：`answerQuery` 命中缓存直接返回（`cached: true`，retrievalMs/generationMs=0），计算完成后写缓存；
- 容错：Redis 不可用/解析失败静默降级为未命中，不阻塞主链路；
- 语义保护：带 `goldChunkIds`（ground truth）的评估请求**不读不写缓存**，保证指标语义。

## 4. 预期效果

| 场景 | 优化前 | 优化后 |
| --- | --- | --- |
| 简单查询 | 13.45s | ~2~4s（跳过重排 + 缓存） |
| 宽泛查询（Multi Query） | 13.45s+ | N 路 embedding 合并 1 次 API + 仅 1 次重排 |
| 重复查询 | 13.45s | ~5ms（缓存命中） |

## 5. 验证

- `npx tsc --noEmit` 通过。
- 压测建议：先发一遍请求（预热缓存），再对比首次与命中耗时；重启 API 服务后生效。
